2. System Model and Trust/Data-Flow Summary

What LORE Is (System Purpose)

LORE is a semantic governance framework — a structured method for making identity, authority, evidence, provenance, and lifecycle explicit in any governed corpus. The public repository is a Phase-1 bootstrap scaffold: schemas, a validator, a status registry, governance documents, test fixtures, and ~130 corpus volumes. It is self-referential: LORE governs its own corpus using LORE's own rules.

Actors and Roles

ActorRole / Trust Level
Author (Steve Gibbons)Sole authority root. May assign author-only statuses. Holds root signing keys. All promotion, publication, and governance decisions.
AI Agents (e.g., this assistant, Copilot)Agent-writable statuses only. May draft, inspect, hash, classify, report. May NOT promote, modify INTAKE/raw, or emit author-only status.
Reviewers (invited)Read-only against public draft; full private corpus access by invitation. Evidence-only report deliverable into INTAKE/.
GitHub Actions CIRuns validator + signature gate on push/PR. No write authority. Trust: platform-level (GitHub).
General PublicRead-only access to public draft. Evaluation and citation permitted under provisional license.

Trust Boundaries

  1. Author ↔ Agent: Hardest boundary. Agent-writable vs. author-only status split enforced by validator Check 2 and CI signature gate.
  2. Public Draft ↔ Private Canonical Corpus: One-way reference via OBJREF-PUBLIC-PROVENANCE-001. Private corpus not resolvable from public.
  3. INTAKE/raw ↔ Normalized/Processed: Immutability enforced via SHA-256 manifest (Check 6). chmod a-w advisory only.
  4. Repository ↔ GitHub CI: CI has repo read; no write authority beyond what Actions platform provides. Workflow runs on push/PR.
  5. Reviewer ↔ Corpus: Reviewers produce evidence-only reports deposited into INTAKE/; author governs promotion.

Key Data Flows

  • Artifact creation (agent) → validator (Check 1–10) → pre-commit hook → git commit → CI (validator + sig gate)
  • Author-only artifact → detached .asc signature (author) → provenance.signature + signer_fpr → Check 2 (representation) → CI sig gate (cryptography)
  • INTAKE/raw arrival → lore_freeze_raw.py → manifest → Check 6 verification
  • Reviewer → evidence-only report → INTAKE/ deposit → author promotion decision
  • Agent hat assembly: lore_prompt.py → profile + lens → composed prompt (no network, no writes)

A-01  HIGH candidate  Confirms KF-01/KF-02
Authority boundary is representation-only until --strict is enforced in CI and all existing author-only artifacts are signed
Assessment
FACT (evidenced by DECISION-AUTH-IDENTITY.accepted.md, lore_validate.py Check 2, validate.yml)
Affected elements
Check 2 (lore_validate.py), lore_verify_author_sig.py, validate.yml, all author-only artifacts
Affected assets
Author-only status integrity; CORE-INVARIANT 2 and 11; the entire authority model
Threat scenario
Any writer who can commit to the repository can create a YAML artifact with status: accepted and either author_preseeded: true (migration grace path still accepted) or a reference to any .asc file regardless of content (pos_02_preseeded_accepted_decision.yaml.asc is explicitly a placeholder, not a real signature). Until --strict is enforced and all existing artifacts signed, the migration grace path is a standing bypass.
Preconditions
Write access to repo; migration grace (author_preseeded: true) still accepted; test fixture .asc files are explicitly not real signatures
Potential impact
Status forgery: agent or adversary promotes artifact to author-only status without author action. Undermines the core governance invariant.
Existing evidenced controls
Check 2 rejects unsigned author-only artifacts lacking both preseed and signature reference. CI runs lore_verify_author_sig.py. neg_06_unregistered_signer_forgery.yaml fixture validates rejection of unregistered signer. Sig guard in pre-commit hook checks .gitignore won't swallow .asc files.
Gaps
(1) Migration grace (author_preseeded: true) is accepted until v1.0.0 — exact count of unsigned author-only artifacts in corpus not verified in this assessment. (2) CI runs --strict per validate.yml, but lore_verify_author_sig skips TESTS/fixtures — placeholder .asc files in fixtures are not real signatures and the tool knows this. (3) Key custody (T5) — that the fingerprint in trusted-signers.txt is actually held by the legitimate author — is explicitly acknowledged as unproven.
Options
(a) Batch-sign all existing unsigned author-only artifacts before v1.0.0; remove migration grace. (b) Audit and publish the count of currently unsigned author-only artifacts. (c) Document T5 (key custody binding) as an explicit open risk with planned mitigation path (hardware token).
A-02  HIGH candidate  Confirms KF-03 — (net-new depth)
The hand-rolled YAML parser is the sole enforcement point and has known parser-differential vulnerabilities
Assessment
FACT (TOOLS/lore_validate.py SimpleYAMLParser; KF-03 acknowledges this)
Affected elements
SimpleYAMLParser in lore_validate.py; all governance checks that depend on parsed field values
Affected assets
Integrity of every validator check; TCB per CORE-INVARIANTS.md
Threat scenario
A crafted YAML document that SimpleYAMLParser reads as status: candidate but a conforming YAML parser (used by any downstream consumer) reads as status: accepted. Concrete attack vectors: YAML anchors/aliases (not handled), multi-line scalars, Unicode normalization, tab vs space, comment injection at key positions. The parser strips comments by checking # position without fully accounting for quoted strings; a quoted value containing # preceded by a space could be misparsed.
Preconditions
Ability to submit a crafted YAML artifact; any consumer using a standard YAML library
Potential impact
Validator passes a file; downstream consumer sees different field values including status escalation. Governance bypassed without triggering any check.
Existing evidenced controls
The validator is the only consumer of these files in the current phase. No external YAML consumers are present in Phase-1 scope. The validator is zero-dependency by design.
Gaps
(1) No conformance-mode parser as secondary check. (2) No fuzz testing of the parser. (3) As soon as any external consumer reads these files with a standard library, differential risk becomes exploitable.
Options
(a) Add a secondary validation pass using Python's stdlib yaml (PyYAML) in safe mode — it is available in standard Python installs and would not break the zero-external-dependency contract of the core validator if kept as a separate CI step. (b) Define a strict YAML subset (no anchors, no multi-line, ASCII-safe) and validate that the input conforms before parsing. (c) Accept as known risk during Phase-1 given no external consumers; re-evaluate before v1.0.0.

Single-maintainer governance is a systemic continuity risk; succession and anti-capture controls are unbuilt

A-04  MEDIUM candidate  Confirms KF-06
INTAKE/raw integrity is manifest-verified but manifest itself is unsigned; break-glass records are unenforced
Assessment
FACT (TOOLS/lore_freeze_raw.py, lore_validate.py Check 6, CORE-INVARIANTS.md)
Affected elements
INTAKE/RAW-MANIFEST.sha256, lore_freeze_raw.py, break-glass schema
Affected assets
Raw evidence integrity; CORE-INVARIANT 5
Threat scenario
(1) The manifest itself can be modified to cover evidence mutation — a tamper-evident manifest in git is detectable only if git history is trusted. A force-push or history rewrite that updates both the evidence and the manifest simultaneously is undetectable by Check 6. (2) The break-glass-record schema exists and test fixtures validate it, but there is no enforcement that a break-glass record must be created before exceptional access to raw evidence. The schema is structural, not procedural.
Preconditions
Git push access + ability to rewrite history (force-push), or: absence of enforcement on break-glass procedure
Potential impact
Evidence tampering undetectable within the system; break-glass access with no audit trail
Existing evidenced controls
Manifest is in git history (tamper-evident for normal commits). Check 6 detects mismatches. lore_freeze_raw.py requires explicit regeneration. GitHub branch protection (if set) limits force-push.
Gaps
Manifest is unsigned (no detached .asc); no branch protection configuration evidenced in repo; break-glass procedure is schema-only, not enforced in validator or CI.
Options
(a) Sign the manifest itself as a root act. (b) Enable branch protection on main. (c) Add a validator check that any modification to INTAKE/raw is accompanied by a committed break-glass or intake record.
A-05  MEDIUM candidate  (net-new)
Agent hat/prompt assembly runs arbitrary shell commands (!`...`) in the Bob skill definition
Assessment
FACT (.bob/skills/lore-hat/SKILL.md line: !`python3 TOOLS/lore_prompt.py $ARGUMENTS`)
Affected elements
.bob/skills/lore-hat/SKILL.md; any AI assistant that executes Bob skills
Affected assets
Host filesystem; any tool accessible from the assistant's execution context
Threat scenario
The SKILL.md file injects $ARGUMENTS directly into a shell command: python3 TOOLS/lore_prompt.py $ARGUMENTS. If the AI assistant passes user-supplied lens IDs to this command without sanitization, and the Bob skill runner executes via shell, an attacker who can influence the argument (e.g., through a malicious INTAKE document containing a lens-ID-like string that gets passed through) could achieve command injection. The lens parameter is intended to be a simple ID (e.g., P1-SEC-THREATMODEL) but is not validated before substitution.
Preconditions
Bob skill runner executes via shell; user or corpus content can influence the argument; no shell quoting on $ARGUMENTS
Potential impact
Arbitrary command execution in the assistant's execution context. Severity depends on the Bob skill runner's sandboxing.
Existing evidenced controls
lore_prompt.py validates the lens ID against known lenses and exits with an error on unknown values — so if the Python script is reached, it enforces the allowlist. The risk is between argument substitution and script invocation.
Gaps
No shell quoting around $ARGUMENTS in SKILL.md. The trust model of the Bob skill runner is not documented in this repo.
Options
(a) Quote the argument: python3 TOOLS/lore_prompt.py "$ARGUMENTS". (b) Validate the argument against an allowlist before passing it to the shell command. (c) Clarify the Bob skill runner's execution model and whether shell injection is in-scope for its threat model.
A-06  MEDIUM candidate  Confirms KF-08 — (net-new depth)
Status field conflates lifecycle, epistemic, and authority state; transition matrix has structural gaps
Assessment
FACT/INFERENCE (REGISTRIES/artifact-statuses.yaml; KF-08 acknowledges ontology thinness)
Affected elements
artifact-statuses.yaml transition matrix; Check 3 in validator; all schema status fields
Threat scenario
(1) evidence-only can transition directly to accepted — a single step from the lowest-trust epistemic state to the highest author-only status. This is structurally permitted by the transition matrix and bypasses candidate and proposed review stages. (2) The transition matrix has no way to express "this transition requires a specific actor type" — any Check 3 validation will pass regardless of who triggered the transition. (3) unknown can transition to evidence-only — promoting uncertainty to a named evidence state without specifying what makes it evidence.
Potential impact
Evidence laundering: a low-trust artifact moves to accepted status through a technically permitted but governance-questionable path. Validator passes; human review might not catch it.
Existing evidenced controls
Check 2 still requires author authority for author-only status regardless of transition. Transition matrix is enforced in Check 3. Author is the only one who can actually make the accepted transition in practice.
Gaps
No actor-type constraint on transitions. evidence-only → accepted is a structural shortcut. No documentation of rationale for these permitted paths.
Options
(a) Add commentary to the transition matrix explaining the intent of each permitted path. (b) Consider whether evidence-only → accepted should require an intermediate candidate or proposed state. (c) Explicitly document actor-type requirements per transition as a future hardening path.
A-07  MEDIUM candidate  (net-new)
CI pipeline has an implicit gpg dependency with no version pin, fallback, or availability check
Assessment
FACT (.github/workflows/validate.yml; lore_verify_author_sig.py line 134: return None, None, None, 'gpg not found on PATH')
Affected elements
validate.yml step "Verify author-only artifact signatures"; lore_verify_author_sig.py
Threat scenario
If gpg is not present in the CI runner image, lore_verify_author_sig.py returns a "gpg not found" string — but it is unclear whether this causes the CI step to fail or silently pass. The script returns exit code 1 only if failed > 0; if gpg is missing and all artifacts are "UNSIGNED" (migration grace), exit code is 0 and CI passes without any cryptographic verification. Supply-chain risk: gpg version behavior differences between runner images could produce inconsistent verification.
Preconditions
gpg absent from CI runner; or all artifacts in unsigned/migration-grace state
Potential impact
Signature gate silently passes without performing cryptography. Gives false confidence in the CI gate.
Existing evidenced controls
The script explicitly prints "gpg not found" as a diagnostic. CI step "Import author public key" checks for KEYS/*.asc existence before importing.
Gaps
No explicit which gpg || exit 1 guard. No minimum gpg version requirement documented. No fallback behavior documented.
Options
(a) Add which gpg || { echo "gpg required"; exit 1; } as first step in the CI signature verification stage. (b) Pin the runner to a specific Ubuntu version known to include gpg. (c) Add an explicit test for the "gpg not found" path to the test suite.

A-09  AFFIRM  Confirms KF-11
Strong foundations worth protecting

FACT. The following design choices are independently well-motivated and should be guarded during hardening:

  • Explicit status ontology: Closed enum with transition matrix is the right architecture. The separation of agent-writable from author-only is a sound privilege separation model.
  • Zero-dependency core validator: Removing external dependencies from the TCB is correct minimalist security design. The parser-differential risk (A-02) is a consequence of this choice worth managing, not reversing.
  • Supersede-not-delete: The lifecycle model that forbids true deletion and requires supersession is correct for a governance/provenance system. It prevents evidence destruction.
  • Preserved rationale and uncertainty: The corpus explicitly preserves design reasoning, rejected options, and uncertainty. This is forensically valuable and directly implements CORE-INVARIANT 7 (no fabrication) and 8 (conversation states not flattened).
  • Self-referential dogfooding: Using LORE to govern LORE provides an operational test harness that is more honest than most framework self-assessments. The KNOWN-FINDINGS.md candor is notable.
  • Representation before enforcement (CORE-INVARIANT 10): The staged migration approach (represent first, enforce later) is architecturally sound and avoids the "big bang" hardening failure mode.

4. LINDDUN Candidate Privacy Threats

LINDDUN is applied to all in-scope personal data flows, identity mechanisms, and telemetry paths. LORE's primary users are described as "tech nerds who interact with AI, many of whom are infosec and privacy practitioners" — a sophisticated audience — but the framework itself handles identity, authority, and evidence in ways that create privacy-relevant surfaces. The corpus also contains personal information embedded in the framework's own design records.

L-01  MEDIUM candidate  LINDDUN: Identifying / Non-repudiation
Author's personal email address (steve_gibbons@icloud.com) is embedded in public key, KEYS/README.md, REVIEWERS.md, and REGISTRIES/trusted-signers.txt in perpetuity
Assessment
FACT (KEYS/README.md, REVIEWERS.md, REGISTRIES/trusted-signers.txt — all contain the iCloud email address)
Affected data
Personal email address; OpenPGP key binding; public key published to MIT and Ubuntu keyservers
Affected people
Author (Steve Gibbons)
Privacy harm
Email address is permanently linked to the LORE framework and all signed artifacts. Once published to keyservers, revocation of the UID does not remove historical records. Spam, doxxing, targeted phishing against LORE's author are facilitated. Non-repudiation risk: signed artifacts cryptographically bind the author's identity to specific decisions — this is by design, but creates an immutable public record that may have unintended long-horizon consequences.
Mitigation options
(a) This is an intentional design decision (governance requires a known identity root). Accept as known risk and document it. (b) Consider whether a professional contact mechanism (e.g., a role email or a contact form) would serve the reviewer-access use case without embedding a personal address. (c) The non-repudiation aspect is a feature, not a bug — document it explicitly as such in the privacy model.
OPEN QUESTION
Has the author considered the long-horizon privacy implications of permanently binding a personal email to cryptographic governance records that may persist for decades?

L-05  LOW candidate  LINDDUN: Non-repudiation
Signed governance artifacts create permanent, cryptographically verifiable attribution records; no right-of-correction or expiry mechanism exists for erroneous decisions
Assessment
INFERENCE (supersede-not-delete model; signature architecture; no correction/expiry mechanism evidenced)
Affected data
Signed decision records; author-attributed statements
Privacy harm
The combination of cryptographic signatures + supersede-not-delete creates a permanent, unretractable public record of every governance decision attributed to the author. If an error is made (factual mistake, premature promotion, incorrect attribution), the signed record persists forever. The supersession mechanism creates a correction record but does not remove the original. In a long-horizon governance model this is a feature; in a privacy model it creates a permanent record of mistakes.
Mitigation options
(a) Document this as an explicit design tradeoff in the governance model. (b) Ensure reviewers and contributors understand that their interactions with the corpus may be preserved permanently. (c) For future multi-author scenarios, define what "correction" means and what the retention implications are.

5. Cross-Cutting Security–Privacy Interactions

XC-01  candidate  Security enables privacy, but the same mechanisms create surveillance risk

The cryptographic signing model (A-01, L-01) that provides governance integrity creates a permanent, unforgeable, public record of every author action. This is LORE's intended design. The cross-cutting tension: as the framework scales to multiple signers or community governance (A-03), the non-repudiation model becomes a surveillance tool over contributors — every governance act is cryptographically attributable and permanently preserved. LORE's long-horizon rationale (LH-R2: sousveillance of the authority) acknowledges this as intentional, but it applies to the authority itself, not necessarily to every contributor. This tension needs explicit design resolution before community governance is built.

XC-02  candidate  Agent authority model intersects with AI platform privacy terms

The agent-signing subkey architecture (DECISION-AUTH-IDENTITY.accepted.md, trusted-signers.txt) delegates signing authority to AI agents. If an AI agent holds a signing subkey and signs artifacts, those artifacts are attributed to that agent under a key whose lineage traces to the author. The privacy question: what data was processed by the AI platform to produce that signed artifact? The signed artifact is permanent; the AI platform's data processing may have involved user data or confidential corpus content. No provenance record currently captures which AI platform version produced a generated artifact (KF-07, agent context not realizable).

XC-03  candidate  The "no retention/disposition model" finding (KF-12) has direct GDPR/privacy implications

LORE's supersede-not-delete model preserves everything by default. This is correct for a governance/provenance corpus. However, if LORE is used in any context involving personal data (which Volume 15 explicitly contemplates), the absence of a retention schedule, disposition authority, and legal-hold model (KF-12) creates direct tension with data minimization and right-to-erasure requirements under GDPR and similar frameworks. The framework design must eventually resolve whether "supersede-not-delete" is compatible with personal data obligations, or whether a separate "personal data corpus" with deletion capability is required.
