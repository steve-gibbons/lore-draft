## How to Read This Document

This spec is a **normative synthesis** of the LORE corpus. It exists to bridge the gap
between the conceptual volumes (`SOURCE/`) and the operational scaffold (`TOOLS/`,
`SCHEMAS/`, `REGISTRIES/`). Where the volumes reason about *why*, this spec says *what
must be true*. Where the scaffold enforces a rule, this spec names the rule and traces
it back to its origin.

**Requirement language** follows RFC 2119: MUST, MUST NOT, SHOULD, SHOULD NOT, MAY.

**Corpus references** are written as `[V-N]` for core volumes (e.g. `[V-0]` = Volume 0)
and `[V-NN]` for extended volumes (e.g. `[V-21]`). Scaffold references cite specific
files and line ranges.

**Enforcement status** is noted inline:
- `(enforced)` — a validator check or CI gate currently tests this.
- `(asserted)` — stated as a requirement; not yet tested automatically.
- `(deferred)` — explicitly out of scope for Phase 1; planned for a later phase.

Discrepancies between this spec and the current scaffold are findings, not errors in
the spec. The spec describes the intended system; the scaffold describes what currently
exists.

## Part I — Purpose and Scope

### 1. What LORE Is

LORE (*Linked Objects, References, and Evidence*) is a semantic governance framework
for making **identity, authority, evidence, provenance, and lifecycle explicit** in any
governed corpus or system. [V-0 §2]

LORE's zeroth principle: `[V-0 §6]`

> LORE MUST preserve trustworthy continuity of context across human and machine
> boundaries.

LORE is not a database, authorization engine, AI framework, or compliance tool. It is
context infrastructure — a layer that other systems can use to record not just *what*
was decided, but *why*, *who had authority to decide it*, and *what remains uncertain*.

### 2. Motivating Failure Mode

The fundamental failure LORE addresses: `[V-0 §4]`

> A highly capable system optimizes exactly what it was asked to do, using authority it
> was accidentally given, with context that was incomplete.

Three necessary conditions collapse into one architectural response:
- Capability without context → make context explicit.
- Authority without boundaries → make authority explicit.
- Data without provenance → make provenance explicit.

### 3. Non-Goals

LORE is not: `[V-0 §19]`
- A replacement for IAM, RBAC, ABAC, PKI, or PAM.
- A universal authorization engine.
- A compliance checkbox or GRC platform.
- An AI safety guarantee.
- A substitute for human judgment.

LORE provides the semantic layer. Existing systems consume it. See `[V-50]` for the
complete prior-art relationship map.

### 4. Scope of This Specification

This document specifies:
1. The **core type system** — the irreducible set of semantic primitives.
2. **Normative constraints** on each type, traceable to corpus volumes.
3. **Lifecycle and governance rules** for records in a LORE corpus.
4. **Serialization requirements** — what must survive representation changes.
5. **Authority and delegation rules** — who may assert what.
6. **Validator conformance** — what a conforming validator MUST check.

Domain extensions (cybersecurity, governance, personal context, agent models) are
defined in `[V-5]` and `[V-6]` and are out of scope for this core specification.

## Part II — The Core Type System

The LORE semantic model has eight primitive types. Everything else is extension.
`[V-1 §3]`, `[V-6 §2]`, `[V-18 §21]`

```
OBJECT          — an identifiable entity
OBJECT_REF      — a reference to an object (ALIAS ≠ IDENTITY)
ASSERTION       — a claim made by a source
EVIDENCE        — information supporting or challenging an assertion
AUTHORITY       — the legitimate ability to act or decide within a scope
CAPABILITY      — a bounded, time-limited, delegatable permission
EVENT           — a meaningful state transition
CONTEXT         — circumstances required to interpret any of the above
```

### 2.1 OBJECT

**Definition.** An OBJECT is an identifiable entity within a LORE universe. `[V-1 §4]`

It MAY represent a person, system, service, device, document, organization, process,
or artifact.

**Required fields (schema: `SCHEMAS/artifact-record.schema.json`):**

| Field | Type | Required | Notes |
|---|---|---|---|
| `id` | string | MUST | Stable unique identifier within the corpus |
| `type` | string | MUST | Record type constant (e.g. `"artifact-record"`) |
| `title` | string | MUST | Human-readable label |
| `status` | string | MUST | From closed enum — see §4.1 |

**Constraints:**
- An OBJECT MUST NOT carry implicit authority by virtue of its existence or name. `[V-1 §4]`
- Existence does not imply trust. `[V-2 §3]`

### 2.2 OBJECT_REF

**Definition.** An OBJECT_REF is a reference to an OBJECT. It is not the object
itself. `[V-1 §5]`, `[V-0 §14]`, `CORE-INVARIANTS.md §6`

> **ALIAS ≠ IDENTITY. OBJECT_REF ≠ OBJECT.**

This distinction is a LORE core invariant. A system MUST NOT silently transform a
reference into the referent without preserving the reference wrapper. `[V-1 §6]`

**Required fields (schema: `SCHEMAS/object-ref.schema.json`):**

| Field | Type | Required | Notes |
|---|---|---|---|
| `id` | string | MUST | Identifier of this ref record |
| `type` | string | MUST | `"object-ref"` |
| `target_id` | string | MUST | ID of the referenced object |
| `status` | string | MUST | From closed enum |
| `resolved` | boolean | SHOULD | `false` unless target is locally verified |

**Constraints:**
- `target_id` MUST be a non-empty string. `(enforced — Check 7, lore_validate.py:258)`
- If `resolved: true`, the target_id SHOULD be present in the local corpus.
  If not present locally, a warning MUST be emitted. `(enforced — Check 7 extension,
  lore_validate.py:263–275, collect_corpus_ids())`
- An OBJECT_REF to a target in the private canonical corpus SHOULD carry
  `resolved: false` and document the custody location. `(asserted —
  META-CONTEXT/provenance-backref.object-ref.yaml)`
- References MUST NOT expand authority. An alias for an administrative account does not
  inherit administrative authority. `[V-0 §14]`, `[V-2 §19]`

### 2.3 ASSERTION

**Definition.** An ASSERTION is a statement made by a source about an object,
relationship, capability, or condition. `[V-1 §8]`, `[V-72 §4]`

**An assertion is not truth.** `[V-1 §9]`, `[V-53 §13]`, `[V-72 §2]`

```
ASSERTION ≠ EVIDENCE ≠ TRUTH     [V-9 §2]
```

**Required fields:**

| Field | Type | Required | Notes |
|---|---|---|---|
| `id` | string | MUST | |
| `type` | string | MUST | `"assertion-record"` *(schema: deferred)* |
| `status` | string | MUST | From closed enum |
| `issuer` | string | MUST | Who made this claim |
| `subject` | string | MUST | What the claim is about |
| `claim` | string | MUST | The claim itself |
| `asserted_at` | string | SHOULD | ISO-8601 timestamp |
| `evidence` | array | SHOULD | References to EVIDENCE records |
| `confidence` | string | MAY | Explicit uncertainty signal |

**Constraints:**
- A system MUST NOT treat an assertion as fact merely because it exists or is
  well-formatted. `[V-9 §3]`, `[V-19 §3]`
- Conflicting assertions MUST be preserved, not silently resolved.
  `[V-2 §9]`, `[V-9 §12]`
- An assertion's lifecycle (superseded, withdrawn) MUST be tracked, not deleted.
  `CORE-INVARIANTS.md §5`, `[V-1 §10]`
- AI-generated assertions MUST be distinguishable from human-authored assertions.
  The `issuer` field SHOULD identify the producing agent or model. `(asserted —
  AGENTS.md §2)`

### 2.4 EVIDENCE

**Definition.** EVIDENCE is information that supports or challenges an ASSERTION.
`[V-1 §10]`, `[V-9 §5]`

```
EVIDENCE ≠ AUTHORITY     [V-1 §12]
```

Evidence answers: *what happened?* Authority answers: *who may decide?*

**Required fields:**

| Field | Type | Required | Notes |
|---|---|---|---|
| `id` | string | MUST | |
| `type` | string | MUST | `"evidence-record"` *(schema: deferred)* |
| `status` | string | MUST | From closed enum |
| `source` | string | MUST | Origin of this evidence |
| `collected_at` | string | SHOULD | ISO-8601 timestamp |
| `scope` | string | SHOULD | What the evidence covers |
| `method` | string | SHOULD | How it was collected |
| `sha256` | string | SHOULD | Hash of raw evidence file if applicable |

**Evidence quality factors** `[V-9 §15]`: authority of source, integrity (tamper
evidence), freshness, applicability, completeness.

**Constraints:**
- A valid signature over evidence proves origin and integrity. It does not prove the
  claim is true or appropriate. `[V-9 §18]`, `[V-50 §26]`
- Evidence MUST carry provenance sufficient to answer: *why was this considered
  trustworthy when it was used?* `[V-9 §22]`
- Raw evidence files in `INTAKE/raw/` MUST be recorded in `INTAKE/RAW-MANIFEST.sha256`
  and MUST NOT be modified after recording. `(enforced — Check 6, lore_validate.py:243–295)`
  `CORE-INVARIANTS.md §5`

### 2.5 AUTHORITY

**Definition.** AUTHORITY is the legitimate ability to make decisions, issue
assertions, or grant capabilities within a defined scope. `[V-1 §13]`, `[V-10 §3]`,
`[V-53 §9]`

```
IDENTITY ≠ AUTHORITY ≠ CAPABILITY     [V-1 §20], [V-10 §2]
```

**Required fields:**

| Field | Type | Required | Notes |
|---|---|---|---|
| `id` | string | MUST | |
| `type` | string | MUST | `"authority-record"` *(schema: deferred)* |
| `status` | string | MUST | From closed enum |
| `issuer` | string | MUST | Who granted this authority |
| `subject` | string | MUST | Who holds this authority |
| `scope` | string | MUST | What domain/resource it covers |
| `expires_at` | string | SHOULD | Authority SHOULD be time-bounded |
| `provenance` | object | SHOULD | Lineage to root authority |

**LORE Core-Invariant 11:** *Authority has lineage.* Authority is a traceable chain
of origin and delegation, not mere possession. `CORE-INVARIANTS.md §11`

**Constraints:**
- The LORE author-authority root is identified by OpenPGP fingerprints listed in
  `REGISTRIES/trusted-signers.txt`. `DECISION-AUTH-IDENTITY.accepted.md`
- Author-only corpus status values (`accepted`, `normative`, `canonical`, `verified`,
  `released`, `superseded`, `deleted`) MUST be bound to a registered signer fingerprint
  and a detached `.asc` signature file. `(enforced — Check 2, lore_validate.py:152–184)`
- Cryptographic verification (GOODSIG/VALIDSIG, lineage to root) is the CI gate:
  `TOOLS/lore_verify_author_sig.py --strict`. `(enforced — .github/workflows/validate.yml)`
- An authority record MUST NOT be emitted by an agent without a `delegated:agent` key
  registered in `trusted-signers.txt`. Delegation is currently deferred.
  `REGISTRIES/trusted-signers.txt`, `DECISION-AUTH-IDENTITY.accepted.md §Delegation`

### 2.6 CAPABILITY

**Definition.** A CAPABILITY is a bounded, scoped, time-limited, revocable permission
to perform a specific action on a specific target. `[V-1 §14]`, `[V-10 §5]`, `[V-53 §10]`

```
CAPABILITY ≠ IDENTITY ≠ AUTHORITY     [V-10 §2]
```

Possessing a capability does not by itself justify its use. `[V-10 §25]`

**Required fields:**

| Field | Type | Required | Notes |
|---|---|---|---|
| `id` | string | MUST | |
| `type` | string | MUST | `"capability-record"` *(schema: deferred)* |
| `status` | string | MUST | From closed enum |
| `issuer` | string | MUST | Authority that issued this capability |
| `subject` | string | MUST | Entity that holds it |
| `action` | string | MUST | Permitted action (e.g. `read`, `modify`) |
| `target` | string | MUST | Resource or scope it applies to |
| `expires_at` | string | SHOULD | Capabilities SHOULD be time-bounded |
| `delegation_allowed` | boolean | SHOULD | Whether sub-delegation is permitted |

**Constraint: delegation ceiling** `[V-2 §21]`, `[V-10 §8]`:

```
CHILD_CAPABILITY ⊆ PARENT_CAPABILITY
```

A delegated capability MUST NOT exceed the scope of its parent.

**Constraints:**
- Capabilities MUST have explicit scope. `[V-2 Invariant 1]`
- Capabilities MUST NOT exceed their parent. `[V-2 Invariant 2]`
- Delegation MUST preserve original authority, scope, constraints, expiration, and
  provenance. `[V-10 §12]`
- Break-glass capabilities (emergency access) MUST be pre-issued, time-bounded,
  auditable, and revocable. They MUST NOT become permanent.
  `[V-3 §15]`, `[V-10 §15–16]`, `SCHEMAS/break-glass-record.schema.json`

### 2.7 EVENT

**Definition.** An EVENT is a meaningful state transition in the lifecycle of any LORE
object, authority, or capability. `[V-1 §15]`, `[V-3 §4]`

Events answer: *what happened, to what, when, and why?* A current state without event
history is insufficient. `[V-3 §5]`

**Required fields:**

| Field | Type | Required | Notes |
|---|---|---|---|
| `id` | string | MUST | |
| `type` | string | MUST | `"event-record"` *(schema: deferred)* |
| `status` | string | MUST | From closed enum |
| `event_type` | string | MUST | e.g. `created`, `delegated`, `revoked`, `superseded` |
| `subject` | string | MUST | What changed |
| `actor` | string | MUST | Who caused the change |
| `occurred_at` | string | MUST | ISO-8601 timestamp |
| `rationale` | string | SHOULD | Why this transition occurred |
| `previous_status` | string | SHOULD | For status transitions |

**Constraints:**
- Events MUST NOT be deleted. They MAY be superseded by corrective events. `[V-91 §6]`
- The difference between an action and its meaning MUST be preserved. `[V-92]`
  Cleaning up the record of an action is itself an action requiring an event.

### 2.8 CONTEXT

**Definition.** CONTEXT is the circumstances required to interpret an object,
assertion, capability, or event correctly. `[V-1 §16]`, `[V-53 §16]`

Context is often the missing element. `[V-1 §17]`

**Lifecycle of context:** `[V-1 §18]`, `[V-3 §17–19]`

```
CONTEXT_HINT  →  (validation)  →  CONTEXT_ASSERTION  →  (evidence + authority)  →  TRUSTED_CONTEXT
```

Promotion MUST be explicit. A `CONTEXT_HINT` MUST NOT silently become `TRUSTED_CONTEXT`.
`[V-3 §18]`

**Constraints:**
- A `CONTEXT_HINT` MAY be searched and used for suggestions. It MUST NOT silently
  change state, grant authority, or trigger irreversible actions. `[V-3 §18]`
- Agent-supplied context MUST be treated as `CONTEXT_HINT` unless the agent holds a
  registered authority or the context has been independently verified. `[V-45 §11]`

## Part III — Identifiers, Namespaces, and Universes

### 3.1 Identifiers

An identifier locates an object. It does not authorize it. `[V-7 §2]`, `[V-34 §2–4]`,
`[V-53 §4]`

```
IDENTIFIER ≠ ASSERTION ≠ CAPABILITY ≠ AUTHORITY     [V-34 §4]
```

**Requirements:**
- Every LORE record MUST carry a stable `id` field. `SCHEMAS/artifact-record.schema.json`
- IDs MUST be unique within the corpus scope in which they are used.
- IDs MUST NOT encode authority, capability, or trust. `[V-7 §2]`
- The timestamp-in-UID construction `[V-7 §9, V-34 §13]` is explicitly flagged as
  problematic (information leakage, unnecessary coupling). Implementations SHOULD use
  random or hash-based uniqueness components instead.
- Human-readable names and aliases MUST be stored separately from stable IDs. Aliases
  MUST preserve resolution history and lifecycle. `[V-2 §19]`, `[V-53 §5]`

### 3.2 LORE Universe

A LORE Universe is a bounded namespace and authority domain. `[V-7 §3]`, `[V-34 §6]`

A universe contains: a local root, locally authoritative objects, relationships,
assertions, evidence, and lifecycle information.

**Constraints:**
- A root has authority only within its defined scope. `[V-7 §5]`
- Federation between universes MUST be explicit. It does not imply universal trust.
  `[V-7 §6]`
- The public LORE corpus (`lore-public`) references the private canonical corpus via
  an OBJECT_REF, not a direct object. `META-CONTEXT/provenance-backref.object-ref.yaml`
  The private corpus is not publicly resolvable. `PROVENANCE.md`

### 3.3 Object References and Indirection

`[V-0 §14]`, `[V-18 §15]`

Indirection MUST remain visible. A system MUST NOT silently resolve a reference into
its target without preserving the reference relationship.

This includes:
- `OBJECT_REF` records (structural indirection)
- aliases (naming indirection) `[V-2 §19]`
- context hints (epistemic indirection) `[V-3 §17]`
- imported external content (provenance indirection) `[V-91]`

## Part IV — Lifecycle and Status Governance

### 4.1 Closed Status Enum

Every LORE record MUST carry a `status` value from the closed enum defined in
`REGISTRIES/artifact-statuses.yaml`. `(enforced — Check 1, lore_validate.py:138–141)`
`CORE-INVARIANTS.md §1`

**Agent-writable statuses** (any agent may assign):

| Status | Meaning |
|---|---|
| `candidate` | Drafted; under consideration |
| `proposed` | Formally proposed for acceptance |
| `derived` | Produced from other artifacts; inputs must be recorded |
| `generated` | Machine-generated; inputs must be recorded |
| `evidence-only` | Raw or imported evidence; not yet evaluated |
| `quarantined` | Isolated pending review or investigation |
| `unknown` | Status cannot be determined |
| `unresolved` | Requires resolution before proceeding |

**Author-only statuses** (require registered signer; see §2.5):

| Status | Meaning |
|---|---|
| `accepted` | Author-ratified |
| `normative` | Binding within the corpus |
| `canonical` | Definitive version |
| `verified` | Cryptographically or externally verified |
| `released` | Published release artifact |
| `superseded` | Replaced by another record |
| `deleted` | Logically removed (record persists) |

`AGENTS.md §2`, `REGISTRIES/artifact-statuses.yaml`

### 4.2 Status Transitions

Transitions between statuses MUST follow the allowed paths in
`REGISTRIES/artifact-statuses.yaml`. `(enforced — Check 3, lore_validate.py:187–191)`

Notable paths requiring care:

- `evidence-only → accepted` is permitted but MUST be an author act. It is not an
  authority bypass — Check 2 still applies. See comments in
  `REGISTRIES/artifact-statuses.yaml:55–61` (added per Aegis A-06).
- `candidate → accepted` is the standard promotion path.
- Any transition to a terminal state (`deleted`) is irreversible.
  `REGISTRIES/artifact-statuses.yaml:107`

### 4.3 Supersede, Don't Delete

LORE uses supersession instead of deletion. `[V-91 §6]`, `CORE-INVARIANTS.md §5`

A record that is incorrect or outdated SHOULD be given `status: superseded` and a new
record issued. The original MUST be preserved. Evidence of past state is evidence. `[V-91 §2]`

> "The cleanest artifact is not always the most trustworthy artifact.
> Sometimes the mess is the evidence." `SOURCE/THE-MAKING-OF-LORE.md §6`

### 4.4 Uncertainty Preservation

Non-authoritative artifacts MUST retain uncertainty status. `CORE-INVARIANTS.md §3`
`(enforced — Check 9, lore_validate.py:237–239)`

An agent MUST NOT promote an artifact to an author-only status. `AGENTS.md §1`
An agent MUST preserve uncertainty rather than resolve it by assertion. `AGENTS.md §3.5`

## Part V — Transformation and Provenance

### 5.1 Transformation Records

Every `derived` or `generated` artifact MUST record: `[V-21 §11]`, `CORE-INVARIANTS.md §4`
`(enforced — Check 8, lore_validate.py:231–235)`

- `inputs`: list of source artifact paths or IDs with SHA-256 digests
- `transformation`: name and description of the producing process
- `provenance.created_by`: identity of the producing agent or tool

**Schema:** `SCHEMAS/transformation-record.schema.json`

```yaml
# Minimal conforming transformation record
id: TR-EXAMPLE-001
type: transformation-record
status: derived
inputs:
  - path: INTAKE/raw/source.md
    sha256: <hex>
transformation:
  name: markdown-normalize
  description: Extracted plain text from raw markdown
provenance:
  created_by: agent/example
```

### 5.2 Evidence Provenance Chain

`[V-9 §8]`

Each transformation step SHOULD be traceable:

```
Raw Evidence (INTAKE/raw/)
    ↓  [lore_freeze_raw.py → RAW-MANIFEST.sha256]
Manifest (INTAKE/RAW-MANIFEST.sha256)
    ↓  [Check 6: lore_validate.py:243–295]
Normalized (INTAKE/normalized/)
    ↓  [transformation-record with inputs + sha256]
Corpus Artifact (SOURCE/ or REGISTRIES/)
    ↓  [Check 2: author signature for author-only status]
Accepted Record
```

### 5.3 AI-Generated Content Provenance

Content produced by AI agents MUST be labeled `status: generated` and MUST record
the producing agent identity and transformation inputs. `AGENTS.md §3.6`, `[V-91]`

AI-generated content MUST be distinguishable from human-authored content at the record
level, not only by inference. `CORE-INVARIANTS.md §7`

## Part VI — The Trusted Computing Base

`CORE-INVARIANTS.md`, `[V-50 §4]`

### 6.1 TCB Definition

The LORE Phase-1 TCB consists of three components:

| Component | Role | Integrity mechanism |
|---|---|---|
| `TOOLS/lore_validate.py` | Single enforcement point for all 10 governance checks | SHA-256 of source tracked in git; PyYAML conformance gate in CI (A-02) |
| Author identity and judgment | Root of all authority; sole promotion authority | OpenPGP key `D9B04B5C`; `REGISTRIES/trusted-signers.txt`; detached `.asc` signatures |
| Artifact integrity | Files are what they claim to be | SHA-256 manifests; `INTAKE/RAW-MANIFEST.sha256`; Check 5 and Check 6 |

`CORE-INVARIANTS.md §TCB`

### 6.2 CORE-INVARIANT 10: Representation Precedes Enforcement

> LORE cannot reliably enforce a distinction it does not represent.

This is the architectural principle behind the staged implementation. The split between
`lore_validate.py` (dependency-free representation check) and
`lore_verify_author_sig.py` (cryptographic enforcement) is a direct application of
this invariant. `CORE-INVARIANTS.md §10`

### 6.3 Validator Conformance Requirements

A conforming LORE validator MUST implement the following ten checks. Current
implementation: `TOOLS/lore_validate.py`.

| Check | Requirement | Enforcement |
|---|---|---|
| 1 | Every `status` field MUST be from the closed enum | `lore_validate.py:138` |
| 2 | Author-only status MUST be bound to a registered signer reference and detached `.asc` | `lore_validate.py:152` |
| 3 | Status transitions MUST follow the allowed-next matrix | `lore_validate.py:187` |
| 4 | Record type required fields MUST be present | `lore_validate.py:193` |
| 5 | If `sha256` and `path` are present, the hash MUST match the file | `lore_validate.py:214` |
| 6 | `INTAKE/raw/` files MUST match `INTAKE/RAW-MANIFEST.sha256` | `lore_validate.py:243` |
| 7 | `object-ref` MUST have non-empty `target_id`; `resolved: true` MUST be verified locally or warned | `lore_validate.py:250` |
| 8 | `derived`/`generated` artifacts MUST have non-empty `inputs` list | `lore_validate.py:231` |
| 9 | Unverified proposals MUST retain uncertainty status | `lore_validate.py:237` |
| 10 | `CORPUS-MANIFEST.yaml` MUST pass structural integrity check | `lore_validate.py:297` |

**Additional CI enforcement:**
- PyYAML conformance gate — secondary parse of all `.yaml`/`.yml` files to detect
  parser-differential discrepancies. `(A-02 — .github/workflows/validate.yml)`
- `gpg` availability guard — hard fail if gpg not on PATH before signature gate.
  `(A-07 — .github/workflows/validate.yml)`
- Signature gate — `lore_verify_author_sig.py --strict`. `DECISION-AUTH-IDENTITY.accepted.md`

### 6.4 The Parser-Differential Risk

`TOOLS/lore_validate.py` uses `SimpleYAMLParser`, a hand-rolled zero-dependency YAML
parser, as the sole enforcement point for all governance checks. `CORE-INVARIANTS.md §TCB`

This creates a **parser-differential risk**: a crafted YAML document may parse as
`status: candidate` under `SimpleYAMLParser` but `status: accepted` under a conforming
YAML library used by a downstream consumer. Known attack vectors include YAML anchors,
multi-line scalars, and comment injection at key positions. `(A-02 — KNOWN-FINDINGS.md KF-03)`

**Mitigation in place:** the CI PyYAML gate detects documents that fail conforming
parse. Parser-differential documents (pass `SimpleYAMLParser`, fail PyYAML) are
separately detectable and MUST be investigated. `(.github/workflows/validate.yml)`

The zero-dependency constraint on the core validator SHOULD be maintained. The
conformance gate is a separate CI step. `CORE-INVARIANTS.md §TCB`

## Part VII — Serialization and Interchange

`[V-21]`

### 7.1 Semantic Survival Requirement

LORE semantics MUST survive representation changes. `[V-21 §2]`

A LORE record MUST remain the same record when moved between YAML, JSON, a database
row, or a message payload. The following MUST be preserved:
- Record identity (`id`)
- Status and lifecycle
- Provenance chain
- Signatures and signature references
- Input hashes (for derived/generated records)

### 7.2 Supported Serializations (Phase 1)

The Phase-1 reference implementation uses YAML as the primary serialization format,
with JSON Schema for structural validation.

- Records: YAML (`.yaml`) or JSON (`.json`). `lore_validate.py:74–84`
- Schemas: JSON Schema draft-07. `SCHEMAS/*.schema.json`
- Manifests: line-oriented `<sha256>  <path>` format. `INTAKE/RAW-MANIFEST.sha256`
- Signatures: OpenPGP detached armored (`.asc`). `KEYS/`

### 7.3 Required Fields for Interchange

The following fields MUST be present in any serialized LORE record intended for
interchange:

```
id, type, status
```

Provenance fields (`provenance.created_by`, `provenance.signature`,
`provenance.signer_fpr`) MUST be present on any author-only record. `Check 2`

### 7.4 Unknown Fields

Implementations MUST NOT reject records that contain fields not present in the current
schema. `additionalProperties: true` is the current schema default.
`[V-21 §14]`, `SCHEMAS/artifact-record.schema.json`

Unknown fields SHOULD be preserved, not silently dropped.

### 7.5 Semantic Loss

When translating from a richer system into LORE or vice versa, the converter SHOULD
report which semantic distinctions could not be represented. `[V-21 §19]`

## Part VIII — Authority, Delegation, and Agent Rules

### 8.1 Authority Hierarchy

```
Author (root)
    ↓ [author act: accepted signature]
Author-only corpus status
    ↓ [deferred: agent signing subkey]
Delegated agent authority (future)
    ↓
Agent-writable status only (current)
```

`DECISION-AUTH-IDENTITY.accepted.md`, `REGISTRIES/trusted-signers.txt`

### 8.2 What Agents May Do

`AGENTS.md §1`

Agents MAY:
- Inspect, inventory, classify, hash, compare, validate, report, draft candidates.
- Create artifacts with agent-writable statuses only.
- Implement bounded tooling on feature branches.
- Surface uncertainty, missing evidence, and contradictions.

Agents MUST NOT:
- Assign author-only statuses without a registered `delegated:agent` key (currently
  deferred — no agent key is active). `REGISTRIES/trusted-signers.txt`
- Modify `INTAKE/raw/` or existing `SOURCE/` files.
- Push, merge, publish, sign, or tag commits or releases.
- Invent corpus content or fabricate provenance.
- Resolve uncertainty by assertion. `AGENTS.md §3.5`

### 8.3 Agent Identity Is Not Human Identity

`[V-45 §5]`, `[V-53 §28]`

An agent acting on behalf of a person does not become that person. The delegation
relationship MUST remain explicit in the record's `provenance.created_by` field and,
when the capability-record schema is implemented, in the delegation chain.

### 8.4 Agent Context Handling

Agent-supplied context MUST be treated as `CONTEXT_HINT` by default. `[V-3 §17]`

An agent MUST NOT use a `CONTEXT_HINT` to:
- silently change corpus state,
- grant authority,
- trigger irreversible actions. `[V-3 §18]`

Context promotion from hint to assertion requires explicit human review or a
registered evidence chain. `[V-3 §19]`

## Part IX — Privacy

`[V-15]`

### 9.1 Personal Data Principles

When LORE records contain or reference personal data:

- Data minimization: collect only context required for the stated purpose. `[V-15 §13]`
- Purpose binding: agent access requests SHOULD name the purpose, not request all
  available context. `[V-15 §14]`
- Explainability: users SHOULD be able to ask what information was used, why, and by
  whom. `[V-15 §15]`
- Correction: the corpus SHOULD support correction via supersession. `[V-15 §16]`

### 9.2 Supersede-Not-Delete vs. Right to Erasure

LORE's supersede-not-delete model is designed for governance records. If LORE is used
in any context where personal data deletion obligations apply (GDPR Art. 17 or
equivalent), a separate mechanism for personal-data records is REQUIRED. The
supersede-not-delete model is not compatible with right-to-erasure by default.
`(open — KNOWN-FINDINGS.md KF-12, Aegis XC-03)`

### 9.3 Author Identity

The author's identity (name, OpenPGP fingerprint, email) is embedded in
`REGISTRIES/trusted-signers.txt`, `KEYS/README.md`, and signed artifacts. This is
intentional for governance accountability. The privacy tradeoff (permanent
cryptographic attribution) is a known design decision. `(Aegis L-01)`

## Appendix B — Key Definitions (Normative)

Drawn from `[V-53]`, normative for this specification:

**OBJECT:** An identifiable entity within a LORE universe.  
**OBJECT_REF:** A reference to an object. Never the object itself.  
**ASSERTION:** A claim with an issuer, subject, and evidence. Not truth.  
**EVIDENCE:** Information supporting or challenging an assertion. Not authority.  
**AUTHORITY:** The legitimate ability to act within a scope. Not identity.  
**CAPABILITY:** A bounded, scoped, time-limited permission. Not authority.  
**EVENT:** A meaningful state transition. Not merely a log entry.  
**CONTEXT:** Circumstances required for correct interpretation. Not metadata.  
**UNIVERSE:** A bounded namespace and authority domain.  
**FEDERATION:** An explicit trust relationship between universes. Not universal trust.  
**PROVENANCE:** Origin, history, and transformation chain. Required for derived records.  
**ALIAS:** A human-readable name. Not identity. Not authority.  
**BLAST RADIUS:** The maximum consequence if a capability or authority is misused.
